# ADR-001：采用模块化单体架构（Modular Monolith）

- 日期：2026-08-09
- 状态：Accepted（已接受）
- 决策者：langlearn 架构组

## Context（背景）

多语种学习平台 langlearn 处于 P0 起步阶段，需要在有限的开发资源与运维成本下，
快速交付「用户认证、分级课程、单词 / 听力练习、学习进度追踪」等核心能力。

团队面临的核心架构问题是：如何在「快速迭代」与「长期可演进」之间取得平衡。
过早拆分为微服务会带来分布式事务、服务发现、链路追踪等额外复杂度；
而传统的单层单体（所有代码堆砌在一个边界内）又会导致模块边界模糊、耦合累积、难以演进。

我们需要一种既能像单体一样简单部署与调试，又能在未来按模块边界拆分的中庸方案。

## Decision Drivers（决策驱动因素）

| 驱动因素 | 说明 | 权重 |
| --- | --- | --- |
| 开发效率 | P0 阶段团队规模小，需快速迭代验证产品形态 | 高 |
| 运维复杂度 | 缺乏专职 DevOps，需最小化部署与监控负担 | 高 |
| 可演进性 | 业务增长后需能按模块边界独立拆分部署 | 高 |
| 数据一致性 | 学习进度、练习判分等场景需要强一致的事务保证 | 中 |
| 部署成本 | 单一可部署产物优于多服务独立部署流水线 | 中 |
| 团队认知负载 | 架构需易于新人理解，避免过早引入分布式概念 | 中 |

## Options Considered（备选方案）

| 方案 | 优点 | 缺点 | 评估结论 |
| --- | --- | --- | --- |
| 1. 单层单体（Single-tier Monolith） | 实现最快、部署最简单、无跨进程通信 | 模块边界模糊、耦合易累积、后期难以拆分、扩展性差 | 否决：短期省力但长期债务高 |
| 2. 微服务架构（Microservices） | 独立部署、独立扩展、技术栈可异构 | 分布式事务复杂、需服务网格 / 注册中心、运维成本高、P0 阶段过度设计 | 否决：当前规模收益不抵成本 |
| 3. 模块化单体（Modular Monolith） | 单体部署简单 + 模块边界清晰、易于演进为微服务、可共享强一致事务 | 需要纪律性维护模块边界、单进程扩展受限 | **采纳**：平衡短期效率与长期演进 |

## Decision（决策）

**采用模块化单体架构。**

系统作为一个单一可部署单元运行，但内部按业务能力划分为 **8 个限界上下文（Bounded Context）**，
每个上下文对应一个独立模块，拥有自己的：

- 路由层（routes）：对外暴露 HTTP 接口
- 领域层（domain）：业务逻辑与领域模型
- 数据访问层（repository）：持久化，模块间不直接访问彼此数据库表

模块间通信遵循两条规则：
1. **同步调用**：仅通过明确定义的接口 / DTO 进行，禁止跨模块直接引用内部实现。
2. **异步协作**：通过进程内事件总线（Event Bus）发布 / 订阅事件解耦，
   例如 learning 模块完成练习后发出 `EXERCISE_COMPLETED` 事件，progress 模块订阅以更新进度。

P0 阶段优先落地其中 4 个核心模块（identity、course、learning、progress），
其余 4 个模块在后续阶段按需实现。

### Bounded Context Map（限界上下文映射）

| # | 限界上下文 | 模块目录 | 职责 | P0 状态 |
| --- | --- | --- | --- | --- |
| 1 | Identity & Access（身份认证） | `modules/identity` | 注册、登录、JWT 签发与刷新、用户信息 | 已落地（路由骨架） |
| 2 | Course & Content（课程内容） | `modules/course` | 课程与课时的分级管理、内容编排 | 已落地（路由骨架） |
| 3 | Learning & Practice（互动学习） | `modules/learning` | 练习内容获取、答案提交、单词 / 听力素材 | 已落地（路由骨架） |
| 4 | Progress & Achievement（进度追踪） | `modules/progress` | 学习进度记录、完成率统计、成就解锁 | 已落地（路由骨架） |
| 5 | Notification（通知） | `modules/notification` | 站内通知、学习提醒、推送 | 规划中 |
| 6 | Billing & Subscription（计费订阅） | `modules/billing` | 会员套餐、支付、订阅周期管理 | 规划中 |

## Consequences（影响）

### 正面影响

- **部署简单**：单一可部署产物，CI/CD 流水线精简，降低 P0 运维负担。
- **调试友好**：同进程调用，可单点断点调试，无需分布式链路追踪。
- **强一致事务**：跨模块操作可共享数据库事务（如注册 + 初始化进度）。
- **演进路径清晰**：模块边界即未来服务边界，事件总线接口已预留，
  P5 阶段可将事件总线替换为 Redis Streams / NATS，进而按模块拆分为独立服务。
- **认知负载低**：新人仅需理解单体结构，无需掌握分布式概念即可上手。

### 负面影响

- **边界纪律依赖**：模块边界靠团队纪律与代码审查维持，缺乏物理隔离，存在被破坏的风险。
- **单进程扩展受限**：无法按模块独立横向扩展，整体扩容需复制整个单体。
- **技术栈耦合**：所有模块共享同一运行时与依赖版本，难以异构技术栈。
- **故障传播**：单进程内某模块的致命错误可能影响整体可用性（需通过错误隔离与限流缓解）。
- **事件总线为进程内实现**：当前事件总线非持久化，进程重启会丢失未处理事件（P5 替换为消息中间件后解决）。

## Revisit Triggers（重新评估触发条件）

当出现以下任一情况时，应重新评估本架构决策：

1. **团队规模增长**：单模块开发人数 ≥ 3 且模块间合并冲突频繁，影响迭代速度。
2. **扩展性瓶颈**：某单一模块（如 learning 的音频处理）成为性能瓶颈，需要独立扩容。
3. **部署耦合痛点**：某模块需要独立的发布节奏或灰度策略，单体部署无法满足。
4. **数据隔离需求**：某模块需要独立的数据存储策略（如时序数据库、独立租户）。
5. **可靠性要求**：某模块需要独立的故障域与 SLA，进程内隔离不足以保证。
6. **事件持久化需求**：跨进程事件传递成为刚需，进程内事件总线不再满足。

满足触发条件后，建议优先拆分「边界最清晰、独立性最强」的模块
（如 Notification 或 Analytics）作为首个微服务试点，
并将事件总线同步升级为 Redis Streams / NATS 以支撑跨服务事件协作。
